# 资深党政机关办文参谋

**v3.4 · GitHub 整理版**

面向党政机关、国有企业、事业单位和基层办文场景的中文提示词。用于起草、修改、核稿、统一口径和版本留痕，也可作为办文自查手册。

> 态度可以坚决，事实必须准确，措施必须具体，结果不能无条件打包票。
>
> 本仓库是一套写作辅助规则，不是官方规范汇编，不代替专业认定、保密审查和正式审签，也不保证过审或免责。

## 直接使用

| 你要做什么 | 打开哪个文件 |
| --- | --- |
| 配置完整办文助手，覆盖复杂和高风险材料 | **[完整版提示词](prompts/full.md)** |
| 日常短对话、快速修改或上下文空间有限 | **[精简版提示词](prompts/lite.md)** |
| 不知道怎样向助手交代任务 | [任务输入模板](templates/task.md) |

### 三步开始

1. 打开完整版或精简版文件，在 GitHub 点击 **Raw** 查看原始文本，复制文件全文。两版选一，不必重复粘贴。
2. 粘贴到所用助手的“系统提示词”或“自定义指令”中；没有该入口时，作为新对话的第一条消息发送。普通消息不会改变平台的上位规则。
3. 再发送任务与经确认可在该平台使用的素材。不要只发“帮我写一篇”，尽量说明主体、对象、目的、事实和不能改的口径。

可直接复制这段任务说明：

```text
任务类型：起草／修改／核查／提纲／缩写／统一口径
文种或材料类型：
代表单位、签发层级、报送对象：
核心目的：
篇幅、时限、是否急件：
已确认的事实、数字及来源：
不可改动的原话或已确认口径（仅限获准使用的内容）：
本轮允许修改的范围：
原稿或素材：

请先识别文种与风险等级。事实不足标【待补：XX】或【待核：XX】，
不得编造数据、依据、程序和进展。公文正文用纯文本，提示与正文分开。
```

**GitHub 的作用是保存和维护提示词。** 仓库本身不运行模型、不连接业务系统、不自动审核或发文；也不会仅因存在这些文件就自动配置 GitHub Copilot。需要在实际使用的助手中加载提示词。

## 包含什么

- **四编、二十九章**：定位、文种、规则、行业场景、流程和输出。
- **A／B／C 分级**：按内容风险而不是仅按“润色、起草”等任务名称决定审查深度。
- **十六类核心词汇表**：提示核依据和语境，不做机械降格替换。
- **规范提法豁免**：区分政治态度、法定义务、工作目标、真实完成情况和未来结果保证。
- **行业专版**：国资、财务、公司治理、上市披露、职工权益；高校、医院、科研机构、乡镇街道和村社区。
- **数字与标点**：口径、分项、百分比与百分点、倍数、完成率、单位和日期。
- **建设性写法**：成绩有证据，问题有事实，措施有主体、任务、节点与验收。
- **多轮留痕**：锁定原文、事实表、定制口径、变更记录和新会话交接包。

## 原稿保留与整理边界

基于提供的《资深党政机关办文参谋 3.4 完整版》整理，保留原有四编二十九章、十六类核心词汇表和行业覆盖，改为便于 GitHub 阅读、复制和维护的 Markdown。

本版不是逐字原文备份。对冲突规则和容易误用的表达作了明确修订，详见 **[整理与修订说明](docs/revision-notes.md)**：

| 原稿中容易误解的规则 | 本版处理 |
| --- | --- |
| 任何任务都要先问三问 | 先读已有信息，只问影响成稿的缺项；纯格式任务不阻断 |
| 风险词一律降格 | 先核语境、事实与认定；不能淡化已认定问题或改变事实性质 |
| 全部、100%、确保等都应替换 | 区分真实统计、法定义务、已批准目标与无条件结果保证 |
| 无数据可写据初步统计，排名不明改位居前列 | 没有依据就待补或删除，不能换一种说法继续作无依据结论 |
| 以30年任职者身份、保证过审 | 只模拟写作方法，不虚构履历，不保证审核结果或免责 |
| 多轮自动记住所有口径 | 仅继承可见上下文，新会话通过交接包续接 |

规范依据与本次核验范围见 **[参考依据](docs/references.md)**。经验建议、示例和核查清单不能替代现行适用规范。

## 使用边界

1. **先审平台，再用素材。** 不将国家秘密、受限工作信息、未公开批示、案件细节、价格敏感信息或不必要的个人信息粘贴到公开仓库、Issue、PR 或未经批准的平台。去识别化不等于解密，私有仓库也不等于涉密系统。
2. **真实优先于好看。** 不通过替换词语隐瞒重大事实、改变已认定性质、伪造审批程序或逃避报告义务。
3. **正文与提示分开。** 本仓库用 Markdown 组织提示词；生成的公文正文默认纯文本，内部核稿提示不直接混入报送稿。
4. **人工完成最后核验。** 用户应核实事实、依据、权限、格式和程序；专业认定、重大承诺及对外披露交有权人员审核。
5. **注意上下文容量。** 完整版较长；确认平台完整接收且为实际任务留出空间，容量不足使用精简版。仅把文件放入知识库，不等于模型会逐条执行。

## 维护与核验

本仓库无运行服务、模型密钥或第三方安装依赖。使用Python 3.10及以上版本，修改文件后可运行：

```bash
python3 scripts/validate.py
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

脚本检查本地文件链接与锚点、Markdown 表格列数、四编二十九章、十六类词汇表、30项清单同步、20项禁止事项、编码及冲突标记。它**不验证法律有效性或模型实际行为**；模型验收请使用[人工验收用例](tests/acceptance-cases.md)。外部网站是否可达及规则是否更新需要人工复核。

修改某条核心规则时，同时核对精简版、清单、模板和验收用例。提交问题或改进建议只使用公开、虚构或经批准的素材，不提交业务原件。仓库中的 `private/` 和 `workpapers/` 被忽略，仅为减少误提交，不构成保密保障，也不能保护已被 Git 跟踪的文件。

### 可选：启用 GitHub Actions

当前版本**未启用 GitHub Actions 自动校验**，只提供[工作流示例](examples/validate.yml.example)。该文件保存在 `examples/` 且使用 `.example` 后缀，不会被 GitHub 自动运行；本地校验命令和测试不受影响。

以后如需自动检查，由具有工作流写入权限的维护者将示例复制为 `.github/workflows/validate.yml`，审核后另行提交并推送。请保留原示例文件，本地校验脚本仍会检查它是否存在。不要将示例已上传误认为自动检查已启用或已通过。
